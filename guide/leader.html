00 · who this is for

Team leader's guide

One person per team, running four or five people through a day that ends in a league table. You are not expected to be the best coder in the room — most of the editing will be done by your team's coding assistants. What you own is sequence.

The one sentence that matters Whatever is on your fork when the organiser runs collection is what plays in the league. Push early, push something that runs, improve it after. A brilliant agent that never got pushed scores nothing.

Mechanics live in HACKATHON_AGENTS.md; this page owns ordering and what “done” looks like at each checkpoint. Where they disagree, that one wins on how things work and this one wins on when to do them.

01 · before the day

Install and check

Ideally done the evening before. An install that starts at 09:30 costs the morning. Python 3.10 or newer; no Snowflake account, no config and no build step are needed to play. 

$ git clone <your fork>   # your fork, not upstream — see 04
$ cd sea-of-colours-hackathon
$ pip install -r requirements.txt
$ python scripts/soc.py doctor

doctor is the arbiter, and since v1.45 it names the exact connection it resolved:

  python           3.13.7
  backend          memory
  agents found     1 discovered, 5 routable
  snowflake conn   ~/.snowflake/connections.toml [soc]
  LLM credentials  present
  No problems found.

How much Snowflake does your team actually need?

Less than people assume. Getting this right saves a morning.

You want to…Needs
Play, tutorials, face the heuristicsNothing. No account, no config
Run tests, mint an agent, use the labNothing
Play against V12, or run your own LLM agentA PAT. That's it — the model call is a REST call
Keep seasons in your Snowflake accountThe extras and a schema deploy
The row teams get wrong An LLM seat needs a persistent backend — but persistent does not mean Snowflake. Start the server with SOC_BACKEND=file and you get a durable, replayable store on local disk that accepts LLM seats. The New Game modal then offers File alongside Memory. No Snowpark install, no schema deploy, no warehouse.
✓ Checkpoint. Collect soc doctor output from every team member in a chat thread before the day starts. Thirty seconds each, and it converts the morning's mystery failures into a list you already solved.

02 · groundwork

Learn the game

Nobody can write an agent for a game they have not played. This is not warm-up: the doctrine your team writes in stage 06 is only as good as its understanding of what wins.

Start the server, press Tutorial on the title screen, and you get a chooser with three cards.

CardNightsTeaches
Basic3the loop — orbit, planning, night, praxis
Advanced4the weapons economy: buying, the public arsenal bar, SNAP and chaff
Quick game3nothing — full board, all rules, no films

Do Basic then Advanced. Advanced is the one that matters here, because it teaches what your agent will spend all day reasoning about.

✓ Checkpoint. Everyone can answer: what does a rival learn when you buy a weapon? If the answer is “nothing” they have missed the arsenal bar, and their doctrine will be built on sand.

03 · groundwork

Play a real game

Play the shipped heuristics before you play each other. red_harvest_lite carries no weapons; red_harvest does. Losing to the armed one teaches more in twenty minutes than beating the lite one teaches all morning.

Then play each other. Multiplayer on the title screen opens a public tunnel and gives a scannable link per seat — no install, no account, no firewall change, works from a phone on cellular. A game seats up to four.

Two traps, both learned the hard way It is not hot-seat: everyone opens their own invite link. And a link carrying only ?session=… makes you a read-only watcher — a playable seat needs &player=pN too. If someone is watching rather than playing, that is why.
Host it yourself Never start the server through a coding assistant. That server belongs to the assistant's shell and dies when the session ends; in multiplayer the tunnel dies with it and every guest is dropped mid-game.
✓ Checkpoint. Someone can explain, unprompted, why they lost a specific game. If everyone is still saying “I just need more harvesters”, play another.

04 · the leader's job

Mint the team agent

Early — before anyone writes a line of code. Everything downstream is named after this decision, and renaming later means re-publishing under a new identity.

Fork on GitHub, clone your fork, then:

$ python scripts/soc.py new \
    --team redwatch \
    --name reaper \
    --participants 'Ada Lovelace, Grace Hopper, Alan Turing'
  • --participants is required and is the league's public record. Everyone who touches the agent goes in; a row that names nobody cannot be credited.
  • The label is team_name — here redwatch_reaper. That string goes in every later command and appears in the seat dropdown as REDWATCH_REAPER.
  • It copies V12 wholesale — 47 files, a complete working agent, not a stub. You start at parity with the baseline and differentiate from there.

What minting touches

$ git status --short
?? sea_of_colours/orchestrator_2/harnesses/redwatch_reaper/

One new directory. Nothing shared is edited. No registry, no import list, no central table. That is what lets forty teams work at once without a merge conflict — and why you must never add your agent to binding_registry.py. Doing so breaks the very thing that makes your fork independent.

✓ Checkpoint. python scripts/soc.py list shows your label.

05 · the leader's job

Publish it empty

$ python scripts/soc.py push

This feels pointless. It is the highest-value five seconds of your day. It proves your remote is right, your directory is registrable and your team has a scoring entry — while there is still all day to fix any of those. push refuses if origin is not yours, which catches the person who cloned upstream instead of forking.

✓ Checkpoint. Your agent directory is visible on your fork on GitHub.

How the GitHub side works, in one page

Worth reading once, because every confusing thing that happens later follows from it.

Each team owns a fork. Nobody has write access to the event repo. That is not a precaution, it is the mechanism: one team's push cannot break another's, and there is no queue to join. Your clone has two remotes — origin is your fork and the only place you ever push, upstream is where kit fixes come from and you never push to it.

Nobody opens a pull request. If someone on your team asks whether to PR their agent or branch off the main repo, the answer to both is no — their agent stays in their fork and you never receive a commit from them.

It has to be a real fork, made with the Fork button. Creating an empty repo and pointing a remote at it is what most people mean by “forking”, and from the laptop it is indistinguishable — full history, your own copy, push works. What is missing is GitHub's link back to the event repo, and the league is collected by walking that repo's forks, so an unlinked copy is never found and never scored with no error anywhere. soc doctor flags it (v1.47). Renaming a fork afterwards is fine; the link survives it.

Your agent is one directory, and that directory is the registration. There is no central list. The kit finds agents by scanning harnesses/ for agent.json files, so minting writes one folder and touches nothing shared. Everything else here is a consequence of that.

soc push is not a plain git push. It runs six steps, and each one is a check that exists because instructions do not survive a deadline:

  1. Is origin yours? It compares your remote against your GitHub login. If you cloned upstream by mistake it stops and prints the exact commands to fix it — your work comes across intact.
  2. Which agent is yours? Found by the agent.json scan. With more than one fork present it asks, via --agent <label>.
  3. Has anything changed outside your directory? If so it refuses, and lists what.
  4. It stages only your agent directory.
  5. It commits, with <label>: update agent unless you pass -m.
  6. It pushes to your fork. If your branch moved underneath you — a teammate pushed, or you pulled upstream on another laptop — it rebases and retries automatically, twice.
The step that surprises people A single edited file anywhere outside your folder blocks the push, even though the commit would never have included it. That strictness is deliberate: at the end of the day only your directory is lifted out of your fork, so a change outside it would not travel — your agent would quietly behave differently in the league than it does on your laptop. Revert it with git checkout -- <path> and push again. If a change outside really is necessary, that is a change to the kit, so raise it rather than forcing it in.

Step six is safe for the same reason. Because every team's commits touch different directories, histories interleave with nothing to resolve — which is why the rebase can be automatic rather than a question. If one ever does conflict, something outside your folder moved; get an organiser rather than forcing it.

Pushing is not entering Your fork is where your agent lives. An organiser collects the forks at the end to assemble the league, fetching each agent directory into a separate staging area. So keep pushing as you go: whatever is on your fork at collection time is what plays.

06 · the heart of the day

Give your agent its first weapon shape

Start from the truth that V12 cannot fight:

$ python scripts/soc.py weapons --agent tabula_v12

  1. the agent knows it owns a rack            FAIL
  2. the play is offerable and compilable      FAIL
  3. the offer explains itself                 FAIL
  4. doctrine says when, and at what tempo     FAIL

Not a bug — the exercise. V12 buys weapons and never fires them. Every fork in the room starts from an agent that owns a rack it does not know how to use, and the teams that place well fix that first.

Decide the shape before anyone types

Three questions, ten minutes, whole team.

  1. How many weapons? One done properly beats three done vaguely. SNAP is cheapest to reason about (100 blue, one cell, one hour) and cheapest to afford, so it is the usual first pick. EMP is the crowd-pleaser. Chaff at 300 is hardest to justify and easiest to waste.
  2. What is the one sentence? “We kill the eye that lights their pure, the night they were going to land on it.” If you cannot say it in one sentence, your doctrine will not say it either.
  3. What is it called? Name it now — see stage 07.

The four surfaces

A weapon play is four edits, in order, and each is invisible until the one before it works. That is exactly why teams get stuck and conclude “the model is stupid”. It is almost never the model.

#SurfaceFile in your forkWhat it means
1Know the rack world_view.py
prompt.py		 The night phase is told what you own. Reading it in orbit_policy.py does not count — that is the buying code, which knows by construction
2Offer and compile chat_schema.py
agency.py
packager.py		 Schema permits the verb, menu carries the play, packager passes it through. All three or nothing fires
3Explain the offer agency.py — Option.detail, Option.rationale Bare geometry is not a decision. Say what firing buys
4Doctrine doctrine.py
_v7/orbit_wishlist.py		 When to reach for it, at what tempo. An option nobody is told to want stays unwanted

Check yourself at any point with soc weapons --agent <yours>. It reads your source, needs no model and no credentials, and runs in a second — so it belongs in the inner loop, not at the end of it. It is a smoke test: it answers “have you built this rung”, never “is it any good”.

The anatomy of one weapon option

Rungs 2 and 3 are one object. Here it is, with a team's own flavour on it:

Option(
    option_id="EMP_BONANZA",
    kind="emp",
    title="EMP BONANZA — three of their eyes, one cloud, (14,9)",
    detail=(
        "One EMP, radius 2, 8-hour cloud. Catches rival probes at "
        "(13,8), (14,9) and (15,10) — every eye they have on the "
        "north seam. Costs 200 blue and one hour-slot."
    ),
    execute_lines=["EMP_BONANZA: emp at [14, 9]"],
    rationale=(
        "Their whole northern read is three probes in a 2-cell "
        "huddle, which is a filing error, not a formation. One "
        "cloud blinds all of it for 8 hours. They cannot drop into "
        "cells they cannot see (§3.9.7), so tonight's landing on "
        "your pure at (15,11) is refused — not delayed. Compare: "
        "SNAP is 100 blue and kills exactly one of the three, "
        "which leaves the drop legal from the other two."
    ),
)

Four things there are worth copying:

  • The title is one line and leads with the outcome, not the coordinates.
  • The detail is honest arithmetic — cost, radius, duration, what is caught.
  • The rationale argues against the alternative. This is the single highest-value habit in the harness: the model is choosing between options, so an option that only praises itself competes badly.
  • The name is silly and the content is exact. EMP_BONANZA genuinely is a bonanza — three probes in one cloud.

What the model does with it

Options reach the model grouped by kind. It then argues with itself. A real night, lightly dramatised:

Menu says
GRAB1 — 340 red at (7,3), visible, no probe needed.
EMP_BONANZA — three eyes, one cloud, (14,9).
PRSNAP1 — a second probe over your landing at (15,11); insurance, banks nothing.
Thinker
GRAB1 banks tonight and risks nothing. BONANZA banks nothing tonight — it takes away their night. I hold 340 red I can see and they are about to take a pure off me. Denial is worth more than the bank here, and it is only worth it because all three probes sit in one radius; next night they will not.
Also weighed
PRSNAP1 insures the landing for one probe and no blue, but insurance protects my grab and does nothing to their tempo. BONANZA does both — blind them, and my landing is safe by consequence.
Plan
[EMP_BONANZA, GRAB1], posture aggressive.

Which lands in the log, in front of the whole room, as:

[REDWATCH_REAPER] [plan=aggressive: EMP_BONANZA, GRAB1] [predicted=high] moves=11
Why the dialogue is the debugger If your agent keeps declining EMP_BONANZA, the rationale is losing an argument — and you can read exactly which one, on the card, and rewrite the sentence that lost it. That is the loop, and it is far faster than tuning numbers.

Plans worth arguing about

Give the team shapes to fight over. None is the right answer; the arguing is the point.

ShapeThe ideaThe catch

07 · identity

Name your moves. Seriously.

Your agent hands the model a menu with short ids. Out of the box they are inherited from V12 and they are fine: GRAB1, PR2, BL3, PRSNAP1. They are also completely anonymous, and a league table of eleven agents all narrating GRAB1 is a table with no personalities in it.

Rename them. SMASHBURGER, LAST_SUPPER, POLITE_ROBBERY — whatever your team finds funny at 2pm. They live in your own harness directory, so renaming is a change to your fork and nobody else's.

Three benefits, in rising order of usefulness:

  1. Identity. Your turns are recognisable in a shared replay, which matters when the room is watching.
  2. Debugging. Grep a whole season for your own vocabulary and find every turn that reached for that play.
  3. Diffing. In the lab you compare your fork against V12 on the same turn. When both say GRAB1 you must read carefully to see whose is whose. When yours says SMASHBURGER1, you don't.
Be silly about tone, never about content These names are not cosmetic to the model — they are in the prompt and it picks moves by id. Call a cautious vision move NUKE and you have quietly told the model that option is aggressive. SMASHBURGER for a smash on your own pure seam is perfect; SMASHBURGER for a defensive probe is a bug you will spend an hour not finding.
Rename all of it, not most of it An id is written where the option is minted, in the line that executes it, and in any doctrine or wishlist that recommends it by name. PRSNAP appears in three files. If doctrine still says “prefer PRSNAP” after you renamed the option to BODYGUARD, you have recommended a move that is not on the menu. That exact bug shipped here once: nothing crashes, the agent just quietly stops taking a play you thought you had recommended. Grep your folder for the old name before you call it done.

08 · how the team works

The cycle

The mistake is five people taking turns at one keyboard. The build is one person's work for an hour; knowing what to build is everyone's, and it happens at the same time.

Build · 1–2

Implement the four surfaces. Head down, few opinions, keeps pushing.

→ an agent that fires

Scout · 1–2

Play V12. Lose to it. Work out how to exploit it.

→ a list of nefarious moves

QA · 1–2

Run seasons and lab turns, read cards, feed transcripts to the assistant.

→ a ranked list of what's broken
Why the scouts matter more than they sound Every agent in the room is descended from V12, including everyone else's. A weakness you find in V12 while playing it is, on the day, a weakness in most of the field. Playing the baseline is competitive research, not warm-up — and it needs no code, no credentials and nobody's permission, so it starts the moment the build track does.

The loop, once the build lands

  scout finds a move ──► build implements ──► QA runs seasons + lab
        ▲                                              │
        └──────────────  ranked feedback  ◄────────────┘
                    (leader keeps the list)
                              │
                          push between
                          every round

Push between rounds, not at the end. A fork you pushed an hour ago is a fork you can go back to.

Collating feedback — the leader's stage

By now four people have opinions and three contradict. Turn that into one ranked list before anyone edits.

  1. Write the complaint as an observation, not a fix. “It bought chaff on day 2 with no rival in vision” beats “make it buy chaff later”.
  2. Attach evidence — a lab board and seat, or a turn number in a season card. An unevidenced complaint costs an hour and finds nothing.
  3. Rank ruthlessly. You will implement two or three, not nine.
  4. Cut game-rules disagreements. Those are for the organisers, not your afternoon.

Benchmark against your own past self

This is the trick that tells you whether you are improving or just changing. Snapshot before a round of edits:

$ python scripts/soc.py share --agent redwatch_reaper --out v1.socfork
$ python scripts/soc.py grab v1.socfork --as-name reaper_v1
  installed redwatch_reaper_v1 — 50 files
  repointed from redwatch_reaper, so both can run side by side

Now improve the real one freely, and when you want to know if it worked, play the new against the old:

$ python scripts/soc.py season --p1 redwatch_reaper --p2 reaper_v1 --seed 99

Far sharper than “we beat the heuristic again”. Beating the bot proves you are competent; beating yesterday's self proves you are improving.

Snapshots are for you, not the league soc push --agent publishes one directory. Push your real agent and leave the _v1 copies local. A team that publishes five variants has five half-agents in the table instead of one good one.

09 · the cheap bit

Evaluate — the three ways to test an agent

There are exactly three, they answer different questions, and they cost wildly different amounts of time. Teams routinely do only the slow one and then wonder why the result is inconclusive.

ModeAnswersCostsPAT?
Lab — one frozen turnWhy did it choose that?~20s a takeyes
Headless — a whole seasonDoes the doctrine survive an arc?~15s a turn, unattendedyes
Play against itWhat is it like to face?a real sittingyes

Do them in that order. The lab tells you what your agent is thinking, the season tells you whether that thinking survives contact, and playing it tells you the thing neither will ever print — whether its weapon does what you imagined when you named it.

Seasons are separate processes writing to separate stores, so just run them at once. 

$ python scripts/soc.py season --p1 redwatch_reaper --p2 red_harvest --seed 11 --name A --quiet &
$ python scripts/soc.py season --p1 redwatch_reaper --p2 tabula_v12  --seed 22 --name B --quiet &
$ python scripts/soc.py season --p1 redwatch_reaper --p2 reaper_v1   --seed 33 --name C --quiet &
$ wait

Measured on this kit: three full seasons in 19 seconds wall clock at 241% CPU — they genuinely run in parallel rather than queueing. Seasons with an LLM seat are far slower because they are dominated by inference latency rather than CPU, which is precisely why parallel matters more there, not less. Three LLM seasons cost roughly what one costs in wall-clock time.

Vary the opponent, not the seed. Each of the three answers a different question:

OpponentAnswers
red_harvestAre we competent?
tabula_v12Do we beat the baseline the field is built from?
reaper_v1Was today worth it?

The fast lane: one frozen turn

A frozen turn is a real turn from a real season, snapshotted the instant before a seat planned. Cast your fork into that seat and compare against V12's decision on identical information. This is where you learn why, which a season score never tells you. 

$ python scripts/soc.py lab      # list the turns and forks
$ python run_web.py             # then open /lab in the browser

Arm the seats from the ARMS control if you want to see how your fork behaves against a rack, then cast it from the AGENT tab. A take comes back in about twenty seconds and brings its reasoning with it. The lab clones the board and writes only to its own directory, so nothing you do here can reach a live game.

The third lane: play against it yourself

The one teams forget, and the one that catches the embarrassing stuff. Start a server, hit Play, and pick your own agent for the opposing seat — it takes its turn automatically after you transmit, you do not invoke it. 

$ SOC_BACKEND=file python run_web.py
An LLM seat is refused on the Memory backend Deliberately, and in these words: “those play on a persistent backend so the season, and the agent's reasoning for every turn, are still there to replay afterwards.” A match you cannot reopen teaches you nothing. Any persistent backend clears it and file needs no Snowflake account, so SOC_BACKEND=file is the answer for almost everyone.

Play three or four nights, not one. You are not looking for the score — you are looking for the moment you say “why would it do that”, because that sentence is the highest-quality bug report your team will get all day.

Will the server see a newly minted agent? It depends on one flag. python run_web.py has reload on by default: minting writes new .py files, the watcher notices, the server restarts itself, and the agent appears in the New Game dropdown and the lab within about ten seconds. --no-reload builds the roster once and will not see it — verified, with soc list showing the agent while that server's own roster still did not. Since --no-reload is the right flag for a long game, the trap is set exactly where it hurts most: mint before you start the server, not after. Hard-refresh the tab either way.

Feed the transcripts to your coding assistant

Every season writes a Markdown card per turn, and one combined file:

reports/seasons/<NAME>_<id>/all-cards.md     (paste this to an agent)
reports/seasons/<NAME>_<id>/cards/           (one file per turn)

A heuristic season's combined file runs about 550 lines — small enough to paste whole. This is the highest-leverage thing QA does all day: hand over the cards and ask why, not what. “Here is the season. On night 3 we declined EMP_BONANZA with three probes in radius. Read the rationale and tell me which argument lost.”

Geometry faults especially fall out of this fast — an agent firing one cell off the cluster, or insuring a landing it was never going to make, is obvious in a transcript and nearly invisible in a score.

A season that “ran fine” may not be yours Without credentials an LLM seat silently falls back to the built-in heuristic. A headless season says so in these words — if you see it, your result is not a measurement of your agent: 
  WARNING: 14 turn(s) fell back to the built-in heuristic — the model was
  not reached, so that part of this season is not your agent's.
✓ Checkpoint. One lab diff you can explain, and one season you have actually watched. A score you have not watched is a rumour.

10 · the last hour

Final polish and final push

Stop editing earlier than feels comfortable. The last hour is verification, not features.

$ python scripts/soc.py doctor        # clean?
$ python scripts/soc.py list          # still listed?
$ python scripts/soc.py season --p1 redwatch_reaper --p2 tabula_v12 --days 3
$ python scripts/soc.py push -m "final"
The failure this prevents A team whose final refactor broke discovery, pushed at the buzzer, and enters the league as a directory the loader skips.
✓ Checkpoint. Your fork carries the agent you intend to enter, and it ran a season within the last thirty minutes.

11 · the organiser

The league

The organiser collects the field into a separate staging checkout — not this repo, not anyone's fork. Attendees pull from upstream all day, and forty entrants landing here would hand the room a conflict. 

$ python scripts/soc.py collect --dry-run   # lists the forks it can see
$ python scripts/soc.py collect             # assembles ../soc-league
$ python scripts/soc.py league

Collection resets before each run, so it is a snapshot of the forks as they stand rather than an accumulation. It will not take a fork's tabula_v12 (every fork has one; the baseline comes from upstream) and will not silently resolve two forks claiming the same name.

appendix

Why your agent vanished

Worth understanding, because when an agent “does not appear” this is always the reason.

Minting writes a directory containing an agent.json. Nothing registers it explicitly. When the binding registry is imported it scans the harnesses directory for anything holding an agent.json, validates each, and folds the valid ones into the routing table. That import-time scan is the whole mechanism.

Two consequences, and both catch people:

  • A fresh process sees your agent immediately. soc list, soc lab, soc season and soc doctor each start Python anew.
  • A running server depends on whether it is watching. The roster is built when that process imports the registry, so the only question is whether it has imported since you minted. python run_web.py has reload on by default: the new files trip the watcher, the server restarts itself, and the agent lands in both the New Game dropdown and the lab cast list within about ten seconds. --no-reload imports once and will not see it until you restart by hand — and that is the flag a long game should be using, so the trap sits exactly where it hurts most. Hard-refresh the tab either way; the page caches the roster it was served.
The one-line habit Mint before you start the server, not after. It costs nothing and it sidesteps the whole question.

Where it can silently not appear

SymptomCauseFix
Not in the dropdown, but soc list shows itServer started --no-reload before you mintedRestart, hard-refresh
Missing everywhere, no errorInvalid agent.json — usually no participantssoc doctor prints it under PROBLEMS
Listed but not selectableNo menu_labelAdd one
Seat does nothing all nightNo PAT — the harness falls back silentlysoc doctor

One typo cannot stop the room A malformed manifest removes that one agent. Everyone else's still loads — deliberately.
